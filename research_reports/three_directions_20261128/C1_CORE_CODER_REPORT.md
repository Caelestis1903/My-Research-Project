# CODER IMPLEMENTATION REPORT | C1 core

The C1 core implements the approved 2,048-pair bank cap per active condition and 2,048 draws per event. C2 samples from the entire ordered C0 candidate pool, using the same condition capacity as C3. C3 samples strictly positive raw P0 fixed-EMA E10 margins. Both store aligned targets clipped to [−5, 5] and share draw positions. C4 uses the C3 bank and draw law with hard labels. The initial roster contains twenty C2/C3 jobs and records C4 as `NOT_TRIGGERED`. [Design](C1_EXECUTION_DESIGN.md) · [Bank implementation](../../experiments/three_directions_20261128/memory_bank.py)

The adapter uses the stock P0 transaction through E10. It compares initialization and every ordered batch and current pair receipt to the committed A1.P0 trace, then checks the complete E10 online and fixed-EMA hashes and step. Its boundary receipt includes the E10 optimizer, loader and RNG digests. At E11 it passes the applied pair and loss reduction to the shared Direction A transaction. Recovery rebuilds the selected bank from frozen C0 input and compares its ordered conditions, indices, offsets, signed targets and digests with the serialized state. [Adapter](../../experiments/three_directions_20261128/c_step.py)

The C1 protocol verifies the scientific gate, the C0 input accounting, and the original A1/B1 source snapshot. It binds the new source, exact P0 job config, Train/Validation identity, C0 inputs, A1 controls and warmup references. Each control retains its original complete RunSpec, journal and completion hashes, endpoint metrics and RAM readback receipts alongside its logical C arm. Source and journal identities for the new jobs are stage-specific. [Protocol](../../experiments/three_directions_20261128/c1_protocol.py)
