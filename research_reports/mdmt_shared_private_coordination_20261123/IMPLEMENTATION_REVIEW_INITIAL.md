## 3. Bugs and deviations

- **MAJOR D2-R1 — Resumed anchor skips startup acknowledgment.** At `training.py:376–380`, a worker resumed at E10, E25 or E40 appends the fork residency sample to `measured` before its first baseline batch. At `training.py:329–336`, `allocate()` treats the nonempty measurements list as proof that `ALLOCATION.json` was published. The supervisor keeps that card startup-pending at `scheduler.py:284–292` for the remaining lifetime of the worker, even when fresh telemetry qualifies the card. A mocked run of `training.worker` resumed from E10, passed diagnostics, and reached the E11 allocation callback with zero fresh memory calls and no receipt. Track whether the startup receipt was published independently of the occupancy sample list, then verify the supervisor can admit another worker on that card.
- **MAJOR D2-R2 — Executable source closure is incomplete.** Importing the D2 CLI imports 11-22 `scheduler.py`, which executes 11-22 `state.py` through its top-level `from .state import generation, request`. The `cli.py:59–69` input allowlist and `s0.py:39–47` source manifest omit `experiments/conditional_history_shared_update_20261122/state.py`. An independent loaded-module comparison confirmed the missing path. Its import-time bytes can change without changing the reviewed implementation hash or source-manifest validation. Bind this module to the pinned donor closure, or remove that runtime dependency using the same reviewed telemetry path.
- **MAJOR D2-R3 — An exposed CUDA command bypasses S0 stage gates.** `s0.py:356–376` exposes `gpu-fidelity` as its own CLI action. That action loads real data, constructs CUDA models and executes the first and tail optimizer updates without the stop controls, passing review or live resource checks in `cli.py:158–171`. The coder report advertises the command. Keep `joint_fidelity` available to the staged smoke, and route CUDA execution through the checked entry point.
- **MAJOR D2-R4 — Completed fork work disappears from failed physical attempts.** `diagnostics.py:201–305` retains per-fork counts and wall times in a local list and returns the list only after all forks finish. `training.py:227–243` publishes it only after full anchor completion. If a later fork fails, the attempt receipt at `training.py:432–439` contains baseline-only `physical` counters. It loses the earlier forks' completed optimization/evaluation work, and `scheduler.py:139–157` later publishes only the accepted anchor's branch costs. This prevents the required separation of successful and retry compute. Record completed diagnostic work per physical attempt before the full anchor result is accepted, and include those counts and timing in attempt costs. Keep scientific endpoint acceptance at the existing whole-anchor boundary.
