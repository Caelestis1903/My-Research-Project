3. **Blocking findings**

**C1 — MAJOR, B3 still blocking: live peer owner schema conflicts with real production writers.** Design §5.3 B2 requires accepting independently authenticated legitimate peer progress and rejecting fraud. In `stage_F0_successor_v15.py:1632`, `owner_matches` uses the same expected `{pid: child_pid, worker_id, nonce: child_invocation_nonce}` for worker lock and GPU lock; `1667–1668` requires both predicates. Actual `TrajectorySupervisor.run` at `run_search_claim_worker.py:1325` writes the worker lock with **supervisor PID/start-ticks/PGID and supervisor worker nonce**, retained for its lifecycle. That nonce differs from each child's invocation nonce. The child does not replace the worker owner. Therefore any newly changed legitimate CLAIMED peer member is rejected by `verify_deferred_no_mutation:1742–1756`, despite valid live locks.

The actual retained owner record was independently read before temporary-directory cleanup. It showed supervisor/worker PID **2121052**, worker start-ticks **37866694**, worker nonce **22e768b8de24432f9616d4501f55806a**; child/canonical PID **2121581**, child start-ticks **37872487**, claim/invocation nonce **abe84fa6ae1647feaf80f1ab1407e176**. These match the writers and disprove the helper's worker-owner assumption. This is observed data, not a reconstruction of missing raw files.

GPU owner has a second bootstrap-stage mismatch: `stage_F0_run.py:2560` initially writes PID/host/index/UUID/claim time. Full nonce/start-ticks/canonical identity is written later in trajectory setup (`1792–1819`). The peer fixture pauses at `canonical_claim_after`, before that enrichment, and its read owner contains only the initial fields. The helper at successor `1633–1638` demands full claim fields even at this stage. A valid join can use canonical/status child's PID/start-ticks/full-key/nonce, supervisor's CHILD_STARTED invocation linkage, worker lock/control supervisor PID/start-ticks/worker nonce, GPU's child PID/index/UUID, and held flocks; full GPU fields can strengthen the check when actually published. The implementation must compare the actual distinct schemas, not require a child-owned worker lock or fields not yet written.

The new real peer test does **not** detect this defect: it establishes the peer claim before launching deferring worker0, then captures `before_races` at test `1865–1867`. The peer wrapper at `1655–1674` only emits administrative heartbeat while paused. No canonical/status/run/attempt member changes during deferral. `capture_f140_state` ignores heartbeat files and `verify_deferred_no_mutation` authenticates only changed members, so `_authenticated_peer_progress` is never invoked for that unchanged peer. The test supports coexistence/no-peer-stop, not successful authentication of newly changed peer work. Correct joins and exercise a claim/state change after the deferring child's pre-spawn snapshot.
